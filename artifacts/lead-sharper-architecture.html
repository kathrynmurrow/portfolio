The strategic problem

Most AI tools forget the user the moment the session closes.

The dominant pattern in AI coaching tools today treats every conversation as a fresh start — re-explain context, re-establish trust, re-introduce the patterns that matter. The result is a tool that feels intelligent in the moment and disposable across moments. Lead Sharper was built around the inverse premise: continuity is the thing that turns AI coaching from a parlor trick into infrastructure. Sessions that build on each other. Memory that persists across devices. Coaching modes that hold their stance over time. The architecture decisions are downstream of that single strategic claim.

Architecture decisions

Six decisions that shaped the build.

Each version forced a tradeoff. Most weren't about what to build — they were about what to refuse to build, what to defer, and what to architect for now versus later. These are the six that mattered most.

01 / Security boundary

Serverless proxy, not direct API call

Speed of build vs. shareability

Putting an API key in the browser is acceptable for a single-user prototype and unacceptable the moment the tool might be shared. Moved the inference call behind a Vercel function before adding authentication. The proxy then became the right place for retry logic, input validation, and rate limiting — all of which would be needed anyway.

02 / Persistence layer

Cloud database with row-level security

Zero-config simplicity vs. real continuity

Browser storage is fast and free, but locked to one device. Real continuity required a backend, which required authentication, which required per-user data isolation. Chose Supabase over Firebase because row-level security policies let the database itself enforce isolation — no application bug can leak data between users.

03 / Authentication

Magic-link auth, not OAuth

Familiar pattern vs. lower friction

OAuth is what most SaaS products do. It's also four extra clicks, an account dependency, and a configuration burden. Magic-link via email is one input, one click, signed in. For a tool meant to feel like a private journal, friction at the front door shapes the entire experience.

04 / Memory architecture

Relevance-scored injection, not full context dump

Maximum recall vs. signal-to-noise

Sending all memories every turn works at five entries and breaks at fifty. Built a lightweight scorer combining recency, type weight, keyword overlap, and mode affinity that surfaces the top twenty most relevant memories per turn. No embeddings, no vector database — just enough infrastructure to keep context lean as conversations accumulate.

05 / Audience scope

Two products, one codebase — not one tool for everyone

Reach vs. fit

The temptation was a single coaching tool flexible enough for any user. The honest answer was that calibration for a senior practitioner actively underserves an earlier-career user, and vice versa. Architected a persona layer beneath the mode layer so the same UI and infrastructure can serve distinct audiences with different system prompts — deferred building the second persona until the first was battle-tested.

06 / Reliability stance

Four small fixes, not a rebuild

Polish vs. pragmatism

The instinct when something feels off is to start over. Most of the time, what's actually broken is mundane: token limits set too low, no retry on transient errors, memory architecture that worked at five entries but breaks at fifty. A focused reliability pass — proxy plus retries plus token budget plus memory filter — fixed more than any redesign would have.

The principle underneath the build

If you're building an AI tool for "anyone," you're building for no one. Pick the user explicitly. Build for them with full specificity. Earn the right to expand by being indispensable to that user — not by being mediocre for everyone.

The stack

Boring infrastructure, on purpose.

Production AI fails not because the model is wrong but because the surrounding system is fragile. Every choice below was made to push complexity down the stack so the surface — prompts, modes, memory — could stay sharp.

Inference Anthropic Claude (Sonnet 4) Strong instruction-following on multi-mode prompts. Generous context window for memory-heavy turns.
API gateway Vercel serverless functions Hides the API key, handles retries with exponential backoff, validates input size, logs errors.
Auth + database Supabase (Postgres + magic link) Row-level security policies make per-user data isolation a database guarantee, not an application concern.
Frontend Vanilla HTML, no framework Single-file app loads in 60ms with no build step. Complexity belongs in the prompts and data layer, not the UI.
State persistence Auto-save on every turn Drafts persist to local storage, conversations to Postgres optimistically, theme preference per user.
Memory architecture Relevance-scored injection Keyword overlap + recency + type weight + mode affinity. No embeddings — just enough to keep context lean.
Build process

From prompt to production in six iterations.

Each version solved a specific failure mode of the previous one. The pattern wasn't planned in advance — it emerged from real usage. Each iteration was a single concentrated decision, not a feature dump.

v1Prompt-only
The crude prototype

A single system prompt pasted into Claude's web interface. Worked beautifully in the moment. Forgot everything between sessions. Confirmed the coaching value; revealed continuity as the missing piece.

v2Browser app
HTML wrapper with browser storage

A custom interface with multi-mode coaching stances and IndexedDB-backed memory. Solved within-browser continuity. Locked the user to one device and exposed the API key in the client.

v3Hardened
Serverless proxy + reliability pass

Moved the API call behind a Vercel function. Added retry logic, input validation, raised the token budget. The tool could now be shared without exposing the key — and stopped truncating responses mid-thought.

v4Memory layer
Relevance-scored memory injection

Replaced "send all memories every turn" with a scoring function. Conversations got noticeably sharper as memory volume grew rather than degrading. Deferred vector search as premature for the data scale.

v5Cloud sync
Supabase backend with row-level security

Migrated persistence from browser to Postgres. Added magic-link authentication. Memory and conversations now follow the user across every device they sign in from. The architecture commitment to multi-user isolation was built in from this point forward.

v6Current · in deployment
Persona-layer architecture, sanitized public demo

Added a persona layer beneath the mode layer to enable distinct audiences without sharing context. Built a sanitized public version alongside the personal one, both running on shared infrastructure with database-enforced isolation. Deploying through May 6.

Operating method

How I approached the build.

The same diagnostic logic that shapes my enterprise work shaped this one — clarify the real problem, define the right structure around it, and build the conditions required for execution to hold.

01 Diagnose

Identified continuity, not intelligence, as the missing piece in current AI coaching.

02 Govern

Established data isolation, security, and key handling as architectural non-negotiables.

03 Enable

Built the infrastructure (proxy, auth, memory) that makes the coaching surface possible.

04 Iterate

Six versions, each solving a single concrete failure mode surfaced by real usage.
